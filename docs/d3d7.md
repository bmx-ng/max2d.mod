# Experimental Direct3D7 backend

**Disabled for now. Direct3D9 is the minimum supported Direct3D backend.**
The experimental BRL graphics foundation and new Max2D adapter remain in the
source tree, behind `?disabled`, for future work on suitable hardware. Existing
BRL.D3D7Max2D remains disabled as before. The implementation below is historical
work in progress, not a supported backend.

## Design and implemented paths

`BRL.DXGraphics` supplies a new SuperStrict windowed D3D7 foundation, replacing
its disabled legacy implementation. Window messages enter BlitzMax through
`bbSystemEmitOSEvent`, retaining the normal system events and polled input.
A native bridge uses the Windows SDK's DirectDraw/D3D7 COM definitions and
structures; it does not depend on Pub.DirectX's commented-out D3D7 interfaces.
The old `BRL.D3D7Max2D` module remains disabled. Its private driver conventions
are not an API compatibility target for this implementation.

The Max2D adapter uses the shared core for ordered triangle batches, primitives,
text, images, atlas regions, coordinate mapping and input conversion. Native
code implements:

- Straight-alpha ARGB managed textures, nearest/linear sampling, dynamic edits,
  and edge padding for devices requiring power-of-two or square allocations.
- Capability checks for the five blend modes. `MASKBLEND` uses fixed-function
  alpha testing at byte alpha 128, including vertex/drawing alpha.
- CPU triangle clipping, including UV and tint interpolation, because D3D7 has
  no scissor state. Virtual resolution and letterboxing use core mappings.
- Viewport clears and backbuffer readback, including RGB 16/24/32-bit conversion.
- Windowed blit presentation with optional vertical-blank synchronization.
- A retained CPU copy of each image for re-upload following surface restoration.
  This adds memory overhead. Edits made while minimized are retained; drawing
  is skipped until the window is available again.

## Current limits

- One window; no exclusive fullscreen, widget attachment, resizing or positioning.
- No render images or mipmaps. Requests fail explicitly. `MIPMAPPEDIMAGE` is
  rejected by `Max2DSupportsImageFlags`.
- Requires 32-bit ARGB texture support and fixed-function texture modulation.
  Linear filtering and individual blend modes are advertised from device caps.
- Only basic surface restoration is implemented. Display-mode/device replacement,
  real surface-loss recovery and suspension need testing and further work.
- Pixel accuracy, filtering, blending, input, timing and recovery have not been
  validated on a working D3D7 implementation. Neither have 32-bit builds.

## Build and deferred tests

From the SDK root:

```
bin\bmk.exe makeapp -r mod\max2d.mod\tests\d3d7_probe.bmx
bin\bmk.exe makeapp -r -t gui mod\max2d.mod\examples\d3d7_hello.bmx
bin\bmk.exe makeapp -r mod\max2d.mod\tests\d3d7_render.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d7 mod\max2d.mod\tests\smoke.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d7 mod\max2d.mod\tests\viewport.bmx
```

Start with `d3d7_probe`: it calls the driver directly so that creation failures
remain visible (BRL's general graphics API catches creation exceptions in
release builds). Then run `d3d7_render`, `smoke`, `viewport` and the interactive
hello example. The rendering test covers the 127/128 MASK boundary, drawing
alpha, all blend modes, non-power-of-two images, edits, presentation and reopening.
The shared viewport test checks every pixel in its clipping cases.

On the development Windows 11 ARM64 Parallels VM, native `DirectDrawCreateEx`
succeeds but `QueryInterface(IID_IDirect3D7)` returns `E_NOINTERFACE` (0x80004002).
This blocks native rendering tests in that environment; it does not establish
that D3D7 is unavailable on every Windows 11 system. Runtime testing is deferred.
No translation wrapper is installed or bundled.
