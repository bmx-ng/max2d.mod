# Native Direct3D9 backend

Use `Framework Max2D.D3D9Max2D` on Windows. This backend uses
`BRL.DXGraphics` for the native window, event handling and device lifecycle,
with `Pub.DirectX` bindings. It does not require SDL3.

## Implemented features

Implemented: ordered triangle batches, primitives, images, atlas views, text,
nearest/linear filtering, dynamic image uploads, viewport clipping, virtual
presentation, render images, target/backbuffer readback and all five Max2D blend modes.
`MASKBLEND` discards alpha below 0.5 in the pixel shader (127/128 for byte
alpha), including the drawing alpha. Managed textures survive the presentation-interval resets
performed by DXGraphics.

Current limits:

- One window, with windowed, borderless and runtime exclusive fullscreen modes.
  Create the window normally, then use `SetFullscreen`; exclusive creation through
  `Graphics(...,depth)` remains unsupported in the new Max2D backend.
- Mipmaps are advertised only when device capabilities and format support
  permit automatic generation for both ordinary and render textures.
- Pixel shader 2.0 and separate alpha blending are required. Older devices
  requiring square/power-of-two textures also require matching render-image sizes.
- Programmatic resize/position are supported for owned windowed contexts; leave borderless first.
- Recoverable device loss skips drawing until a reset succeeds. Fatal driver
  errors still raise an exception; automatic device replacement is not implemented.
- Testing so far is Windows 11 ARM64 in Parallels, running x64 binaries.
  Physical Windows GPUs and 32-bit builds remain untested.

Start with `examples/d3d9_hello.bmx`. From the SDK root:

```
bin\bmk.exe makeapp -r mod\max2d.mod\examples\d3d9_hello.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d9 mod\max2d.mod\tests\smoke.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d9 mod\max2d.mod\tests\viewport.bmx
bin\bmk.exe makeapp -r mod\max2d.mod\tests\d3d9_render.bmx
```

Run each resulting executable. Successful tests print a pass message. The
rendering test checks blend results, dirty texture updates, non-power-of-two
texture coordinates, two presentation resets and context recreation. The
viewport test checks 24 complete output images.

## Device recovery

Drawing and presentation skip unavailable/minimized frames, with a short
wait at Flip to avoid spinning while unavailable. The application
must continue pumping events and calling `Flip`; reset retries happen there.
Image edits and new images are retained on the CPU and uploaded when drawing
resumes. Existing managed textures survive Reset. Each batch reapplies its
render state, including viewport, clipping, texture and blending. Skipped draws
are discarded, so the application should redraw its scene each frame as usual.
Backbuffer readback throws while unavailable rather than returning invalid data.
Closing a lost context remains supported.

DXGraphics now preserves reset parameters across attempts, sends the lost
callback once per reset cycle and the reset callback only after success, and
retries a transient `D3DERR_DEVICELOST` reset result on a later Flip. Its optional
occlusion-query wait is skipped when presentation did not succeed and checks
for device loss while waiting.

Build `tests/d3d9_recovery.bmx` with `-ud d3d9_recovery_test`. The test-only
DXGraphics fault injection is excluded from normal builds. It exercises lost
and not-reset states, repeated transient reset failure, callback counts,
deferred image edits/creation, real device Reset, native minimize/restore,
unavailable readback and close/reopen. These checks passed in the Windows VM.
They do not substitute for physical-GPU, suspend/resume or display-change tests.

The recovery rules follow Microsoft's [D3D9 lost-device documentation](https://learn.microsoft.com/en-us/windows/win32/direct3d9/lost-devices).

## Render images

D3D9 implements the existing `Max2D.Core` render-image API: `CreateRenderImage`,
`SetRenderImage`, `DrawImage` and `ReadRenderImage`. Common state management,
viewport mapping and sampling-feedback protection are unchanged. See
`examples/d3d9_render_images.bmx` for two rendering passes with transparency.

Render textures store premultiplied colour; the shader converts sources as
needed for each blend mode. Readback returns straight RGBA, matching the other
backends. Reading a different image leaves the selected drawing target intact.
New render images are initialized transparent.

Render images use D3DPOOL_DEFAULT and must be released before device Reset.
The existing DXGraphics lost-device callback releases these native resources;
they are recreated lazily, transparent, after recovery. This also applies to
resets caused by changing Flip synchronization. Planned shared-API borderless
transitions and programmatic window resizes preserve render-image contents using temporary system-memory snapshots;
see [window modes](window-modes.md). Otherwise, redraw their contents after a
reset (or each frame); CPU-backed ordinary images retain their data. Rendering
attempted while unavailable is discarded, just as it is for the window.

`tests/d3d9_targets.bmx` covers target composition, all blend modes, alpha and
orientation, readback without changing the active target, clipping, feedback
rejection and recreation after Reset. `tests/d3d9_recovery.bmx` also checks
render-target resources across failed reset attempts.

## Mipmaps

Use `MIPMAPPEDIMAGE` with ordinary images or render images. Combine it with
`FILTEREDIMAGE` for trilinear minification; without filtering the sampler uses
nearest texels and the nearest mip level. Query `Max2DSupportsImageFlags` first.
`examples/d3d9_mipmaps.bmx` compares filtered drawing with and without mipmaps.

Ordinary mipmapped textures receive premultiplied uploads; CPU pixels and locks
remain straight RGBA. This prevents invisible RGB from bleeding into lower
levels. Render images already store premultiplied colour. D3D9 generates the
chain with linear reduction, including when nearest mip sampling is selected.

Generation is requested before sampling a dirty texture. Uploads, target clears
and target drawing invalidate the chain. Unchanged draws reuse it. The existing
`mipmapGenerations` statistic counts these explicit requests, not opaque driver
work. Managed image contents survive Reset and their chains are refreshed;
render images are recreated transparent on unplanned resets and should be redrawn
as described above. Borderless transitions restore their snapshots and regenerate
mipmaps on subsequent sampling.

The shared core still isolates mipmapped animation frames and rejects packed
atlas mipmaps. No new image API is introduced. `tests/d3d9_mipmaps.bmx` covers
minification, update ordering, partial edits, transparent fringes, target changes,
odd dimensions, animation isolation, atlas rejection and reset recovery.

D3D9 autogeneration hides the lower levels from `GetLevelCount`, which returns
one even for a complete automatically generated chain. The tests verify sampled
pixels instead. The backend requires `D3D_OK` from the format-support checks;
`D3DOK_NOAUTOGEN` is explicitly treated as unsupported. See Microsoft's
[automatic mipmap documentation](https://learn.microsoft.com/en-us/windows/win32/direct3d9/automatic-generation-of-mipmaps).

## Borderless validation

`tests/d3d9_borderless.bmx` passed in Windows 11 Parallels: repeated mode changes,
monitor coverage, window geometry restoration, one lost/reset callback pair per
transition, virtual input conversion, managed-image retention and exact translucent
render-image retention after changing their contents. Existing target/blend,
mipmap and BRL.D3D9Max2D regression tests also passed.
`examples/d3d9_borderless.bmx` is built for Windows: F10 toggles, Escape exits.
Physical GPUs, mixed-DPI monitors and device loss during the transition still
need runtime validation.

## Window resizing and positioning

`GraphicsResize(width,height)` updates the client size and resets the backbuffer.
The new Max2D backend preserves render-image contents using the same snapshot
path as borderless transitions. Same-size requests do not reset the device.
`GraphicsPosition(x,y)` places the client area's top-left in desktop coordinates
without resetting the device. Window client sizes use 96-DPI logical units. Position arguments use native
desktop coordinates under the process's current DPI awareness.

Max2D refreshes its viewport after resizing, retains an explicit virtual
resolution and maps input using the new window dimensions. Failed native changes
refresh the selected canvas's cached settings before rethrowing. If native resize
succeeds but device reset is deferred, keep processing events and calling Flip
for recovery, as with borderless transitions.

Attached contexts, exclusive windows and borderless windows reject these
operations; resize also requires a single selected owned device. The legacy
BRL.D3D9Max2D wrapper can use direct `canvas.Resize`/`canvas.Position` calls,
followed by `SetGraphics(canvas)` to refresh its rendering state. It retains its
existing reset rules; render-image snapshots belong to the new Max2D backend.

`tests/d3d9_window_management.bmx` covers growth and shrinkage, same-size requests,
client position, backbuffer coverage, retained render images, reset callbacks,
and borderless round trips after resizing. `examples/d3d9_window_management.bmx`
uses F5 to resize, F6 to move, F10 for borderless and Escape to exit.

The window-management and borderless regressions passed in the Windows 11
Parallels VM, together with `tests/brl_d3d9_window_management.bmx` for legacy
canvas resize/position and image rendering. The interactive example was built.
Mixed-DPI monitor moves and reset failure during resizing remain unvalidated.

The window-management example renders its labels at native backbuffer resolution
while the scene keeps an 800x480 virtual resolution. F5 alternates 640x384 and
the original 800x480; labels are not downsampled with the scene. The regression
compares native text pixels before and after resize/borderless round trips.

## Exclusive fullscreen

`SetFullscreen(True,width,height,hertz)` selects an exact enumerated mode on
D3D9's default adapter. Zero dimensions use the current drawing dimensions; zero
hertz chooses the highest matching refresh rate. An unavailable mode is rejected
before changing the window. Windows on another adapter's monitor are rejected;
move the window to the default adapter's display first. Query support with
`Max2DSupportsFullscreen()`.

The device is reset with exclusive presentation parameters; returning to windowed
restores the desktop display mode, saved client area and window decorations.
Transitions between exclusive and borderless pass through windowed mode and can
therefore involve two resets. Max2D uses its snapshot path to retain render images
through deliberate transitions. Legacy directly-created exclusive contexts keep
their existing activation callbacks; runtime fullscreen uses actual device-reset
completion to signal callbacks. Minimize/focus loss can still cause ordinary device
loss: redraw render images after such recovery and keep pumping events and Flip.

The Windows VM demonstrated that D3D9 changes an initially DPI-unaware process
to DPI-aware on its first exclusive transition. That change is process-wide and
is not undone on exit. D3D9 window creation and resize normalize dimensions to
96-DPI logical units. Restoration saves the physical client area, while input
conversion queries actual client coordinates separately from backbuffer pixels.
Native desktop position values can change when awareness changes even when the
physical position is unchanged. This does not add mixed-monitor DPI event handling
or normalize unrelated windows owned by other modules.

If Reset returns device-lost, the requested mode remains pending and the call
throws; continue processing events and Flip for recovery. A hard reset failure
attempts to reset the previous presentation parameters and restore window geometry.
Errors still propagate, and callers should query the current mode/settings.

Use `examples/d3d9_fullscreen.bmx`: F5 resize, F6 move, F10 borderless,
F11 exclusive, Escape exit. It chooses an enumerated 1280x720 mode when available
and otherwise uses another enumerated mode. Labels use native backbuffer resolution.

`tests/d3d9_fullscreen.bmx` passed in Windows 11 Parallels at 200% scaling,
starting both DPI-unaware and already DPI-aware. Checks include exact display
mode changes/restoration, invalid-mode rejection, all three mode transitions,
retained translucent targets, client-input mapping, physical window restoration,
resizing and new-window creation after the awareness change, minimize/restore
recovery, and desktop restoration on exclusive close. The window-management and
legacy BRL regressions also passed. Hard reset failure rollback, transient failure
during a mode change, physical GPUs and multiple monitors still require validation.


### Compatibility with BRL.Max2D

This adapter uses `TD3D9GraphicsDriver.CreateLogicalGraphics` to opt into 96-DPI
logical window sizing and maps native input coordinates separately. Ordinary
BRL `CreateGraphics` keeps the previous native client-coordinate convention,
including when the application is already DPI-aware. Existing BRL.Max2D programs
do not inherit the new adapter's sizing convention.
