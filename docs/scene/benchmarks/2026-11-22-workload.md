# Combined scene, lighting and effects workload

Measured on 22 November 2026 using an Apple M4 Max (16 logical CPUs, 64 GiB RAM),
macOS 27.0.1 (26A434), release builds, SDL3 GPU/Metal and OpenGL. Desktop apps and
idle Windows/Ubuntu VMs remained open; builds and benchmark runs were sequential.
These are local comparative measurements, not cross-engine or cross-hardware results.

Raw results: [Metal](2026-11-22-workload-metal.csv),
[OpenGL](2026-11-22-workload-gl.csv).

## Reproduce

From the BlitzMax SDK directory, build both executables before running either:

```sh
bin/bmk makeapp -r -o /tmp/scene_workload mod/max2d.mod/tests/scene_workload.bmx
bin/bmk makeapp -r -ud max2d_gl -o /tmp/scene_workload_gl mod/max2d.mod/tests/scene_workload.bmx
/tmp/scene_workload > /tmp/scene_workload_metal.csv
/tmp/scene_workload_gl > /tmp/scene_workload_gl.csv
```

Use appropriate paths on other platforms. `--quick` runs a small functional smoke
check. The window is blank because rendering targets an offscreen 640×480 image.
Skip CSV lines beginning with `#`; successful runs end with a PASS marker.

## Workload and protocol

[scene_workload.bmx](../../../tests/scene_workload.bmx) combines:

- An automatically cached background with 1,000 ordinary sprites.
- A clipped, automatically cached group containing 128 interactive sprites with
  normal/specular materials, followed by bloom and an image-alpha mask.
- Eight coloured point lights, two shadow maps and four rectangular occluders;
  grouped lighting and spatial selection enabled.
- Eight retained text labels in an unlit HUD layer and CPU alpha-mask picking.

Each case runs three 120-frame trials, each preceded by 30 warm frames. Cached
frames change nothing; mask-only frames move the mask; lights-only frames move
all eight lights. Combined frames also move 16 receivers and the world camera.
Scene updates use a fixed 1/60-second delta. A single fixed-position pick is made
per frame. Images, materials and application scratch objects are shared/retained.

The combined case then runs 20 consecutive blocks of 3,000 measured frames
(60,000 frames per backend), without rebuilding the scene or warming between
blocks. Explicit collection happens before and after each block. This is a
checkpointed allocation soak, not an uninterrupted presentation loop.

`update_us`, `prepare_us`, `pick_us` and `render_submit_us` isolate CPU call
intervals. Render includes clear, scene rendering, flush and any driver waits.
`drained_us` includes these operations, statistics sampling and a one-pixel
readback at the end of the block. A readback also drains work before timing.
There is no Flip or vsync. These numbers are neither GPU elapsed time nor FPS.
Unlike the earlier microbenchmark, this test drains once per block, not per frame.

Allocation totals use cumulative GC bytes around each frame's update, preparation,
picking and rendering. Printing, snapshots, readback and explicit collections
are excluded. Natural collections within these intervals are counted. Heap
in-use means collector heap size minus free bytes after collection; it includes
collector accounting and conservative retention, not just live object payloads.
Native driver memory and process RSS are outside these measurements.

## Short trial results

Median microseconds per frame across three trials; allocation was identical on
both backends in every trial. All raw rows are retained above.

| Case | Metal render submit | Metal drained | OpenGL render submit | OpenGL drained | Managed bytes/frame |
| --- | ---: | ---: | ---: | ---: | ---: |
| Cached | 3.90 | 65.03 | 12.74 | 84.11 | 624 |
| Mask only | 15.96 | 188.27 | 218.59 | 258.96 | 5,616 |
| Lights only | 106.96 | 465.61 | 857.95 | 890.65 | 11,136 |
| Combined | 101.92 | 444.24 | 915.74 | 960.21 | 11,920 |

Short trials and longer blocks have different queue/drain behaviour; compare
like intervals rather than treating submit time as isolated rendering cost.
The small lights-only/combined timing differences do not establish a speedup.

Retained storage was constant across all cases and blocks: 6,088,640 bytes for
scene composites, 131,072 for shadows and 16,777,216 for lighting map storage
(22,996,928 bytes total). These counters exclude shared source artwork, fonts
and driver-owned storage. Teardown returned all three charged counters to zero.
Stable post-collection memory shows no growth in this finite workload; it does
not establish a general leak-free or allocation-free guarantee.

## Work counters and next optimisation

| Case | Submissions/frame | Captures/frame | Stage passes/frame | Composite hits/frame |
| --- | ---: | ---: | ---: | ---: |
| Cached | 3 | 0 | 0 | 2 |
| Mask only | 11 | 0 | 2 | 1 |
| Lights only / combined | 143 | 1 | 2 | 1 |

Moving lights exercised 128 grouped receiver passes and two shadow rebuilds per
frame on both backends. Grouped lighting is still work per receiver, not one
whole-scene draw. The benchmark checks cache behaviour, grouped/shadow activity,
constant retained storage, zero warmed texture creation and cleanup.

The clearest bounded optimisation is to retain an unchanged prefix of the effect
chain. Moving only the final alpha mask currently reruns the preceding bloom,
even though its input and parameters have not changed. Source capture is already
reused. Reusing bloom's output could remove this redundant work without changing
the public effect API. These measurements do not isolate bloom's cost or predict
the resulting speedup; compare equivalent output and counters after implementation.

Rendering submission/waits dominate the combined CPU interval. There is also
ongoing managed allocation despite stable retained memory. Allocation attribution
and any broader rendering changes should be measured separately. This workload
does not cover tilemaps, particles, ECS simulation, deep trees, text shaping,
real input distribution, mixed artwork or a production game's present loop.
