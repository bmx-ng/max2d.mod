# Initial scene benchmark results

Measured 2026-11-21 on an Apple M4 Max, arm64, macOS 27.0.1, with release
builds from the workspace BlitzMax compiler. The library source was at
`421d2fd`; this tranche adds the benchmark and documentation without changing
the runtime implementation.

SDL3 GPU reports its Metal driver. The second executable uses desktop OpenGL.
Builds completed before the recorded runs; backend runs were sequential and the
three worked-example windows were closed. This is a desktop measurement, not
an isolated laboratory run. There are three trials per case.

See [methodology and reproduction](../performance.md). Raw results retain all
trials: [SDL3 GPU / Metal](2026-11-21-macos-arm64-sdlgpu.csv) and
[OpenGL](2026-11-21-macos-arm64-gl.csv). CSV comment metadata is recorded here;
the archived files contain only the header and measurement rows.

## Warming and GC

Every measured update/query/pointer workload allocated **zero managed bytes**,
on both executables and at both sizes. Captured pointer movement actually routes
to a node; an assertion verifies its callbacks before timing.

Ordinary scene rendering allocated **368 bytes per call**, including an empty
scene, at both sizes and on both backends. This is consistent with the outer
render-state scope visible in the implementation, rather than per-node
allocation. It is about 22 KB/second for one render call at 60 Hz.

The tested changing-bloom paths allocated **6,832 bytes per parameter update**
and **6,048 bytes per source-changing frame**, independent of node count.
These are measured totals including scene/effect work, not an attribution to
individual objects. At 60 updates/second that is approximately 410 KB/second
or 363 KB/second respectively, per such workload.

No measured submission interval recorded a collection, and no warmed graphics
trial created a texture. This does not establish absence of GC pauses in a
long-running application: readbacks, setup and application code allocate outside
these intervals.

The flat-tree miss scales with interactive node count. Captured movement avoids
picking and stays approximately constant in this workload. This supports using
capture for active drags; it does not imply that uncaptured hit testing has a
spatial index.

## Graphics submission

Median microseconds per frame, including clear, mutations/drawing and flush.
Readback is excluded from these columns. Driver waiting inside flush is included.

| Workload | Metal 1,000 | Metal 10,000 | OpenGL 1,000 | OpenGL 10,000 |
| --- | ---: | ---: | ---: | ---: |
| `render_empty` | 1.543 | 1.271 | 8.340 | 25.720 |
| `immediate_sprites` | 21.151 | 194.774 | 174.207 | 678.935 |
| `scene_static` | 46.929 | 437.307 | 345.329 | 2004.056 |
| `scene_parent_move` | 55.093 | 552.413 | 191.672 | 1910.490 |
| `scene_one_child_move` | 50.450 | 433.903 | 258.498 | 1691.440 |
| `cached_parent_move` | 4.823 | 27.223 | 118.335 | 444.895 |
| `bloom_parameter` | 30.385 | 192.328 | 421.055 | 1775.639 |
| `bloom_source_move` | 73.810 | 640.597 | 833.042 | 1758.188 |

For the 10,000-sprite Metal workload, static scene submission adds approximately
0.243 ms over equivalent immediate drawing. Both submit three geometry batches per
frame on Metal (eight on OpenGL); scene rendering preserves the immediate
path's batching in this workload.

Cached movement reports one reused output and no captures. Bloom parameter
changes report one stage update and no captures. Source changes report one
capture and one stage update. These are checked by the executable, not inferred
from timing.

Cached movement still has some node-count-dependent CPU work. Reusing pixels
does not promise constant-time traversal or retained GPU rendering instructions.

OpenGL timings include synchronous driver costs in this workload. They must
not be read as a traversal-only measurement or a general
Metal-versus-OpenGL ranking. In particular, stage-only and recapture timing
differences can be obscured by driver waiting.

| Backend | Submit min–max (µs) | Median drained interval (µs) |
| --- | ---: | ---: |
| Metal | 436.143–446.704 | 717.172 |

The drained interval includes a one-pixel readback and instrumentation.
It is not a GPU timestamp, frame budget or present-loop FPS estimate.

## What this supports

- Retained traversal and pointer storage avoid per-operation GC allocation in
  the tested warmed logic paths.
- Plain scene rendering has fixed managed allocation rather than allocation
  proportional to the number of sprites in these cases.
- Cached output and retained effect sources take their intended reuse paths.
- Ordinary sprite scenes preserve batching in the tested shared-image workload.

## Next measurements and optimisation candidates

1. Attribute and reduce effect-update temporary allocations, retaining the
   exception-safe drawing-state behaviour.
2. Profile large cached-subtree CPU validation before adding complexity to its
   invalidation model.
3. Run Windows/Linux and D3D backend coverage separately; these results establish
   only a macOS baseline.
4. Add representative deep hierarchies, mixed textures and long-running GC
   traces if application profiling identifies them as important.
