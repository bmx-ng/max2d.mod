# Effect support-check allocation reduction

Follow-up to the [initial macOS baseline](2026-11-21-macos-arm64.md), on the same
Apple M4 Max and macOS 27.0.1. Source is `0abf6f6` plus the accompanying change
to `CheckScaledBlurTarget` in `effects.mod/scaledblur.bmx`. The benchmark is
unchanged. Both release executables were built before running them sequentially.

Support queries need the target, blend and submission path, but do not need a
temporary virtual resolution or viewport. Selecting the target directly avoids
allocating a full drawing-state scope for each query. Actual drawing passes and
the enclosing operation retain their state-restoration scopes. No public API
changes or scope pooling are involved.

## Managed allocations

Allocator-accounted bytes per measured frame, identical for 1,000 and 10,000
sprites and for both Metal and OpenGL, across all three trials:

| Workload | Before | After | Reduction |
| --- | ---: | ---: | ---: |
| Bloom intensity change, source reused | 6,832 | 3,520 | 48.5% |
| Bloom after moving a captured child | 6,048 | 3,840 | 36.5% |

The measured warmed logic operations still allocate zero bytes. Ordinary scene
rendering and cached-parent movement remain at 368 bytes per frame. No new
textures were created during measured trials. Remaining bloom allocations
include scopes protecting actual rendering; this is not an allocation-free
effect pipeline.

## Timing and verification

Metal median submission times for 10,000 sprites were 196.8 microseconds for
the intensity-change case and 648.8 microseconds for recapture, versus 192.3 and
640.6 in the initial run. These runs do not establish a timing improvement.
The allocation reduction is the useful result; desktop timing and OpenGL driver
waiting remain variable. See the [measurement definitions and limits](../performance.md).

All 17 selected release regressions passed: scene bloom, bloom pipeline, scaled
blur, effect buffers and both shadow pipelines on Metal and OpenGL, plus the
five applicable effect tests on the software profile. Existing checks cover
pixel output, custom target views, caller state and unsupported-effect failure.
Windows and Linux were not tested in this follow-up.
