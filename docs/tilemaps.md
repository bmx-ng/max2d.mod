# Native tilemaps

Import `Max2D.TileMap` alongside a Max2D backend. The module contains native grid
geometry, sparse map storage, rendering and optional ground-depth sorting. Import
`Max2D.Tiled` separately if you want to load maps made in Tiled. No graphics context
is required for geometry or map construction.

## Start without a map editor

Create a `TTileGrid` to define cell geometry, add artwork to a `TTileSet`, then
create a `TTileMap` and populate its layers with `SetCell`. Artwork can come from
loaded images, atlases or pixmaps generated by your code. You can generate terrain
procedurally or change cells during play; no Tiled files or other editor output
are required.

For a small working application, start with [Building a hex board](hex_board.md)
and [examples/hex_board.bmx](../examples/hex_board.bmx). The example generates its
own artwork and demonstrates selecting cells, terrain properties and a range
overlay. The larger [tilemap example](../examples/tilemap.bmx) adds layout switching,
cameras, painting, animation and sprite sorting.

Use this guide as the API reference after trying an example. For gameplay objects
and shape queries, see [objects and collision geometry](tile_objects.md).

## Grid layouts

Choose a layout to match your artwork and movement rules:

| Layout | Typical use |
| --- | --- |
| Rectangular (orthogonal) | Square/rectangular tiles arranged in straight rows and columns; platformers and top-down maps |
| Isometric | Diamond tiles giving a view of a world from above and to one side |
| Staggered isometric | Diamond tiles arranged in alternating offset rows or columns |
| Hexagonal | Six-sided cells for strategy maps, with pointy or flat tops |

```blitzmax
Local square:TTileGrid=TTileGrid.Rectangular(32,32)
Local hex:TTileGrid=TTileGrid.Hexagonal(64,72,ETileLayout.PointyHex,ETileStagger.Odd)
Local flat:TTileGrid=TTileGrid.Hexagonal(72,64,ETileLayout.FlatHex,ETileStagger.Even,18)
Local iso:TTileGrid=TTileGrid.Isometric(64,32)
Local staggered:TTileGrid=TTileGrid.StaggeredIsometric(64,32,ETileAxis.Y,ETileStagger.Odd)
```

Grid configuration is immutable. Both hex orientations support odd and even
staggering. Pointy hexes shift alternate rows right by half a tile width; flat
hexes shift alternate columns down by half a tile height. Parity works the same
for negative coordinates: -1 is odd, -2 is even.

Standard isometric projects each cell origin to
`((column-row)*width/2, (column+row)*height/2)`. Cell (0,0) has its bounding-box
origin at (0,0) and diamond centre at (width/2,height/2). This is an unbounded
coordinate system; there is no automatic translation based on finite map size.

Staggered isometric uses alternating rows (`ETileAxis.Y`) or columns
(`ETileAxis.X`), each with odd/even parity. Adjacent staggered rows are height/2
apart; adjacent staggered columns are width/2 apart. These are diamond cells,
with four edge neighbours. They are not hexagons with six neighbours.

The bounding-box dimensions describe the artwork's grid cell. `sideLength` is
the straight vertical edge length for pointy hexes, or horizontal edge length
for flat hexes. It defaults to half that axis's dimension. Width, height and side
need not describe a regular hexagon: pixel-art proportions are supported. Side
length must be strictly between zero and its axis dimension. Dimensions must be
positive, finite and at most 65536.

A cell origin is its bounding-box top-left, including staggering. In an even
layout, cell (0,0) is shifted. The map origin itself is fixed; changing layouts
does not automatically recenter the map.

- `CellOrigin` and `CellCenter` write local pixel coordinates into `Double Var`s.
- `CellCorner` writes one polygon corner without allocating; `CornerCount` is
  four or six. Diamond corners start at the top vertex. Corners are clockwise in screen coordinates.
- `LocalToCell` tests actual cell geometry, including the sloping corners. It
  finds a cell even when the map contains no tile there. Exact shared polygon edges
  choose the lowest row, then column. Rectangles use half-open bounds.
- `ToAxial`/`FromAxial` and `ToCube`/`FromCube` convert hex coordinates. Cube
  coordinates satisfy q+r+s=0. All non-hexagonal grids reject these conversions.
- `Neighbour` writes one adjacent cell. Rectangular direction order is right,
  down, left, up; standard isometric uses +column, +row, -column, -row.
  Staggered diamonds use a square lattice whose positive directions point
  northeast/southeast for Y staggering and northwest/northeast for X staggering.
  Opposite directions differ by two. Hex directions use axial deltas (1,0), (1,-1), (0,-1), (-1,0),
  (-1,1), (0,1); opposite directions differ by three.
- `Distance` is Manhattan distance on the underlying square lattice for rectangular and
  isometric grids, and hex grid distance for
  hexagons. It does not measure pixel distance or account for obstacles.
- `Range(column,row,radius,ring=False)` returns a newly allocated `STileCell[]`.
  Set `ring=True` for cells exactly that distance away. Results are in stable
  coordinate traversal order, not perimeter order. Radius is limited to 0..1024;
  cache results when the origin and radius have not changed.

Cell coordinates are limited to ±1,000,000. Conversion methods reject invalid
coordinates; `LocalToCell` returns False outside the supported range. Rendering
uses Max2D's Float vertex coordinates, so large world-space pixel positions can
lose subpixel precision. The coordinate limit is not a precision guarantee.

## Tiles, layers and animation

```blitzmax
Local tiles:TTileSet=New TTileSet
Local grass:Int=tiles.Add(grassImage)
Local water:Int=tiles.AddAnimation(waterAnimation)
Local map:TTileMap=TTileMap.Create(hex,tiles)
Local ground:TTileLayer=map.AddLayer("ground")
ground.SetCell(-1,0,grass)
ground.SetCell(0,0,water)

' Inside the drawing loop, after applying the scene camera:
map.Draw(0,0,elapsedMilliseconds)
```

Tile zero is empty. Other tile IDs index shared definitions in the tileset.
`Add(image,frame=0,offsetX=0,offsetY=0)` registers static artwork;
`AddAnimation(image,offsetX=0,offsetY=0)` registers a timed `TImage` animation.
Every animation frame must have a positive duration in milliseconds. Map drawing
uses the explicitly supplied elapsed time, with one shared phase per definition.
The default time is zero. No hidden clock or update task runs.

Artwork uses the cell's bounding-box origin plus its definition offset, ignoring
image handles. For a tall tree anchored to the cell bottom, use an offsetY of
`grid.TileHeight()-image.height`. Trimmed atlas images preserve their original
canvas and therefore keep the same alignment. Use `SetSize` to change display
dimensions and `SetDepth` to change sorting. Keep the source image dimensions
unchanged; register a new definition to replace the artwork.

`SetCell(column,row,id,ETileFlip.Horizontal|ETileFlip.Vertical)` flips artwork
around its logical canvas. It does not mirror the grid. Setting ID zero clears
the cell. Transformations do not change cell properties, picking, neighbours or
region queries.

Additional `ETileFlip` flags apply to both cells and layer sprites:

- `Diagonal` exchanges the artwork axes, swapping width and height while keeping
  the original bottom-left point fixed. Horizontal/vertical flips then act on the
  exchanged axes. The eight combinations cover the rectangular tile symmetries.
- `Rotate60` and `Rotate120` combine to 60, 120 or 180 degrees clockwise about the
  original canvas centre. Horizontal/vertical reflections act on the source axes
  before rotation, matching Tiled's hex renderer. Combining reflections with these
  flags also expresses the remaining hex orientations.
- Combining `Diagonal` with either rotation flag is rejected as ambiguous.

For example, `ETileFlip.Diagonal|ETileFlip.Horizontal` is a 90-degree clockwise
rectangular rotation. A non-square canvas changes its footprint. Definition
positions and sprite anchors still establish the original canvas position before
these transformations; they are not transformed grid coordinates.

Trim offsets, atlas regions and animation frames use the same transform. No
rotated texture copies are created. Artwork culling uses transformed bounds;
chunk selection uses a conservative envelope. Depth sorting keeps the original
cell-bottom or sprite ground-contact key, so art rotation does not reorder it.
Transforming a sprite does not rotate its custom anchor around its ground point:
it follows the same original-canvas rules described above.

Each layer stores occupied 32×32 chunks and reclaims a chunk when its final cell
is cleared. Empty reads allocate nothing. Maps can grow into negative coordinates;
there is no fixed map size. `CellCount`, `ChunkCount`, `Cell`, `CellFlip` and `Clear`
provide basic inspection and editing. `Bounds` returns conservative inclusive
cell bounds, which may remain wider after deletion until `Clear`.

Layers draw in insertion order. Each has `visible`, `opacity` and local
`offsetX`/`offsetY` properties. Layers are never reordered across one another.

## Sorting and movable sprites

`layer.sortMode` defaults to `ETileSort.Grid`. By default, Grid ordering draws cells in their
geometric top-to-bottom, left-to-right order, including the diagonal bands of
standard isometric maps and the half-row offsets of staggered columns. Static
isometric cells use a sorting queue to obtain this order. Existing rectangular
and hexagonal grid layers retain their direct drawing path.

Use `ETileSort.GroundDepth` on a scenery layer to interleave tiles and moving
sprites by their **ground-contact point**:

```blitzmax
Local scenery:TTileLayer=map.AddLayer("scenery and characters")
scenery.sortMode=ETileSort.GroundDepth
scenery.SetCell(3,4,treeTile)
Local actor:TTileSprite=scenery.AddSprite(actorImage,groundX,groundY)
' Update actor.x and actor.y as the character moves.
```

A tile's default depth is its cell's bottom Y, independent of the artwork's
height, offsets, trim or flip. `tiles.SetDepth(id,offset=0,order=0)` adjusts its
ground-contact depth relative to that bottom. This is a supported mutation of a
registered tile definition; use it when artwork depicts a different contact point.

A sprite's x/y is its contact point in layer-local pixels. `anchorX`/`anchorY`
locate that point in its original image canvas; the defaults are bottom-centre.
Image handles are ignored. Sprites also have `frame`, `animated`, `flip`, `visible`,
`depthOffset` and `sortOrder` fields. Set `animated=True` to use the map's elapsed
time and the image's frame durations. Static sprites use `frame`.

Within a GroundDepth layer, items sort by:

1. Ground Y plus the item's depth offset, ascending.
2. Explicit `sortOrder`, ascending (only breaks equal-depth ties).
3. Ground X, ascending.
4. Original submission sequence, preserving exact ties.

Sorting uses map-local coordinates before camera and parent transformations.
Camera rotation does not change the depth rule for the painted artwork.
SetDepth and sprite depth offsets affect ordering only, never drawing position.
Grid mode ignores depth overrides and draws sprites after all tiles in sprite
insertion order. This makes GroundDepth an explicit opt-in for existing layers.

`RemoveSprite` removes one sprite; `ClearSprites` removes all. `Clear` still
clears only tiles. A layer can contain sprites without any occupied cells. Sprites
are culled by their artwork bounds, including anchors; layer offsets and opacity
apply equally to tiles and sprites. Grid picking still returns cells, not sprites.

Ground-point sorting supports ordinary characters and props. It is not a general
3D occlusion solver: large multi-cell buildings, crossing walls or bridges may
require split artwork and explicit layers. Navigation, elevation and collision
rules are not inferred from image overlap.

## ECS integration

The tilemap does not depend on an ECS. An optional game-side adapter can keep
terrain in sparse tile layers and use `Ecs.Flecs` for characters, pickups, doors
and other entities with behaviour. ECS systems remain authoritative for position,
movement and game state. After simulation, update each entity's retained
`TTileSprite` position/frame/visibility, then call `map.Draw` to interleave it with
scenery. Create/remove the sprite when the entity enters/leaves that render layer,
not on every frame.

The existing Flecs examples keep images in a BlitzMax asset array and put numeric
image IDs in native ECS component structs. The same pattern can resolve artwork
for the adapter; a separate entity-to-sprite registry keeps managed rendering
objects alive. ECS ordered queries alone would not merge entities with native
map tiles, so the shared map rendering queue performs the final depth order.

This is an integration approach, not a bundled adapter or a requirement to use
ECS for map cells. Applications using ordinary BlitzMax objects use the same
sprite API.

## Cameras, transforms and picking

`Draw(x,y,time)` applies the current object transform to the entire map, including
cell spacing, then the parent transform and camera. It respects origin, colour,
alpha, blend, viewport and render target. Primitive and image handles are ignored.
All caller drawing state is restored, including when drawing raises an exception.

`Pick(virtualX,virtualY,column,row,x=0,y=0,layer=Null,checkViewport=True)` uses the
same current state and map position. Supply the relevant layer to include its
offset. The coordinates are virtual drawing-surface coordinates; `MouseCell`
performs window-to-virtual input conversion and rejects letterbox
bars and points outside the viewport. Call these while the same camera and
transforms used for drawing are active. Changing the drawing state afterwards
does not preserve an implicit picking snapshot.

Picking identifies geometric cells, independently of visible artwork, populated
cells or obstacles. It does not consume mouse events. Call `layer.Cell` to query
what occupies a picked position. Alpha-based artwork selection, navigation and
physics are separate concerns.

The renderer inverse-transforms viewport corners, expands candidate bounds for
artwork overhang and staggering, and queries visible chunk coordinates. Empty
chunks skip their cells; compatible draws use Max2D's ordinary atlas batching.
It preserves painter's order rather than sorting by texture. It supports rotated
views and render textures without a second rendering implementation.

`drawnTiles`, `drawnSprites`, `drawnTexts`, `drawnImages`, `sortedItems`,
`visitedCells` and `chunkLookups`
describe the last Draw call. `sortedItems` counts entries submitted to a sort queue,
including standard-isometric Grid entries.
Chunk lookups count row/pass queries, not distinct chunks. Work depends on the
visible grid area and tile definitions, not just the number of nonempty cells.
An extreme zoom-out can still be costly; restrict the visible area or switch to a
simpler overview at distant zoom levels. No objects are allocated per visited cell; drawing-state
and transform snapshots are allocated per map/layer. Sorting uses a retained
struct array that grows when necessary, with no object allocation per item after
growth. Visible queued entries are sorted in O(n log n); image references are
cleared after drawing, including after errors. All registered sprites are checked
for visibility each draw; there is no sprite spatial index.

- H: change hex side length.

## Tile properties

`tileset.Properties(tileID)` returns shared, case-sensitive application metadata.
It supports `SetBool`/`GetBool` (BlitzMax `Int` booleans), `SetLong`/`GetLong`,
`SetDouble`/`GetDouble` and `SetString`/`GetString`. Getters accept a fallback for
missing names; a present value of the wrong type throws rather than converting
silently. `Get(name)` returns a typed `TTileProperty`, or Null. Scalar values are immutable;
class values expose mutable member collections. Its `Kind()`
is an `ETilePropertyType`; `AsBool`, `AsLong`, `AsDouble` and `AsString` read it.
`Contains`, `Remove` and `Clear` manage the bag. Empty names cannot be written.

```blitzmax
tileset.Properties(wallID).SetBool("solid", True)
tileset.Properties(waterID).SetDouble("moveCost", 2.0)
tileset.Properties(waterID).SetString("terrain", "water")

' An individual door can override its shared definition.
layer.CellProperties(12, 8, True).SetBool("solid", False)
Local solid:TTileProperty = layer.Property(12, 8, "solid")
If solid And solid.AsBool() Then
	' The game decides what solid means.
End If
```

`CellProperties(column,row)` reads an existing override bag without creating one.
Pass `True` to create it; the cell must be occupied. `layer.Property` resolves an
override first, then the shared definition. Missing properties and empty cells
return Null. A False or zero override is still an override. Removing a name from
an override restores inheritance. Changing a cell's tile ID or erasing it discards
its overrides; setting the same ID, including changing its flips, retains them.
`layer.Clear()` discards all cell overrides along with the cells.

Property dictionaries are allocated only on writing. Shared metadata is stored
once per tile definition, not copied to every cell. Property reads do not allocate
values; scalar writes replace immutable values. Property names such as `solid`, `terrain`
and `moveCost` are application conventions, not built-in physics or pathfinding.

## Region queries

Two methods collect occupied cells:

- `layer.QueryCells(left,top,right,bottom,result)` uses inclusive integer cell
  coordinates. Reversed bounds give an empty result; coordinates must be within
  the supported grid limits.
- `map.QueryRegion(layer,x,y,width,height,result)` uses a rectangle in map-local
  coordinates, including the layer's offset. It checks the actual cell polygon
  for every layout. Only positive-area overlap counts; touching an edge or corner
  does not. Width and height must be nonnegative; zero area gives an empty result.

Both return a `TTileQueryResult`. Omit `result` for a new one, or reuse an existing
instance. Each call clears the previous count and retains buffer capacity. Read
only `cells[0 Until count]`; each `STileQueryCell` contains `column`, `row`, `tile`
and `flip`. Results are snapshots in unspecified order, not live references to
cells. Filter them using `layer.Property` as needed:

```blitzmax
Local nearby:TTileQueryResult = New TTileQueryResult
' Reuse nearby on subsequent movement checks.
map.QueryRegion(layer, playerX, playerY, playerWidth, playerHeight, nearby)
For Local i:Int = 0 Until nearby.count
	Local cell:STileQueryCell = nearby.cells[i]
	Local solid:TTileProperty = layer.Property(cell.column, cell.row, "solid")
	If solid And solid.AsBool() Then
		' Candidate for the game's movement/collision handling.
	End If
Next
```

Queries need no graphics context and ignore cameras, rendering transforms, map
Draw positions, layer visibility/opacity, sprite artwork, trim and animation.
Convert screen input to map-local coordinates before querying it. Region queries
use cell footprints, not artwork bounds or collision shapes. The grid also exposes
`OverlapsRectangle(column,row,x,y,width,height)` for individual cells, using
coordinates local to that grid (without a layer offset).

Small queries look up candidate chunks; large sparse queries scan existing chunks
instead of all empty chunk coordinates. Candidate chunks scan only their relevant
cells. Result storage grows when needed, with no managed object per hit. Scanning
existing chunks creates a collection iterator; this is not an allocation-free API.

The tilemap example shows an orange query rectangle around the actor and purple
outlines on overlapping terrain cells. WASD moves it; B toggles the overlay.
Hovering a populated cell displays its `terrain` property. This is a query demo,
not a movement controller: collision response, slopes and one-way platforms remain
separate work.

Nested class values, deep copying and overlays are described in
[structured properties](tiled_templates.md#native-structured-values).

## Rectangular tile draw order

For rectangular grids using `ETileSort.Grid`, each layer has a `renderOrder`:

```blitzmax
layer.renderOrder = ETileRenderOrder.LeftUp
```

| Order | Rows | Cells within a row |
| --- | --- | --- |
| `RightDown` (default) | Top to bottom | Left to right |
| `RightUp` | Bottom to top | Left to right |
| `LeftDown` | Top to bottom | Right to left |
| `LeftUp` | Bottom to top | Right to left |

This controls which artwork appears in front where neighbouring tiles overlap.
It changes traversal only: cells, picking, collision shapes and layer positions
stay the same. Reversed traversal works across sparse chunks and negative cell
coordinates, without collecting or sorting tiles. Viewport and overhang culling
still limit the visited region.

`ETileSort.GroundDepth` takes precedence and uses its ground-contact,
explicit order and tie-breaking rules. Isometric, staggered and hex grids keep
their geometric order. Grid-layer sprites still draw after the tiles;
object layers retain their separate index/top-down ordering.

`examples/tile_render_order.bmx` compares four identical arrangements of oversized
tiles. The overlapping centre changes colour with the draw order. Space switches
all panels to ground-depth sorting; Escape exits. It supports the usual backend
build conditionals and `--test`/`--screenshot` console arguments.

## Display sizing and text objects

`TTileSet.SetSize` configures a display canvas independently of source image size,
with stretch or centred aspect-fit artwork. Drawing, flips, animation, culling and
cell collision queries use the same sizing. Layers can also contain retained
`TTileText` objects. See [tile sizing and text](tile_sizing_text.md) and
`examples/tile_sizing_text.bmx`.
