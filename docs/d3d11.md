# Direct3D11 backend

Use `Framework Max2D.D3D11Max2D` on Windows. This first implementation supports
resizable windows, borderless and exclusive fullscreen, drawing, ordinary images, render images and mipmaps.
Device removal triggers recreation of the device and its GPU resources.

## Foundation

`Pub.Direct3D11` supplies SuperStrict SDK bindings and dynamically loads device
creation. `BRL.DXGraphics` owns the window, device, immediate context and DXGI
flip-sequential swap chain. Window messages enter BlitzMax through
`bbSystemEmitOSEvent`, preserving normal events and polled input.

The backend requires a hardware D3D11 device with feature level 10.0 or newer,
and DXGI 1.2 (`IDXGIFactory2`). D3D11 is loaded only when requested; importing
BRL.DXGraphics does not impose a D3D11 DLL dependency on existing D3D9 programs.

## Implemented

- Shared Max2D geometry, ordered batches, text, image views and atlas regions.
- RGBA textures, non-power-of-two images, partial image edits, nearest and
  linear filtering.
- All five blend modes, including shader-based `MASKBLEND` at alpha 0.5 after
  texture and drawing alpha are combined.
- Virtual resolution, letterboxing, native overlays, viewport clipping and
  clipped clears, using the shared coordinate mapping.
- Backbuffer readback in physical pixels, with opaque window alpha.
- Render images through the existing `CreateRenderImage`, `SetRenderImage`,
  `ReadRenderImage` and `ClearImage` APIs. Targets start transparent, retain
  contents across presentation and window resizing, and can feed later passes.
  GPU storage is premultiplied; shader sampling and readback preserve the public
  straight-alpha semantics. Sampling the active target is rejected by the core.
- Window resizing and positioning. Resizing releases backbuffer references
  before resizing the swap chain; ordinary textures remain available.
- Minimize/restore handling. Window drawing is skipped while minimized; image edits and offscreen rendering
  remain available. Window readback is rejected until restoration.
- Synchronized and unsynchronized presentation.

Shaders are included as compiled bytecode. Applications do not need a shader
compiler DLL. See [shader rebuilding](../d3d11max2d.mod/shaders/README.md).

## Displays and fullscreen

These operations use the [shared Max2D window-mode API](window-modes.md).
The original D3D11-prefixed functions remain compatibility wrappers.

`Graphics(width,height,0)` creates a window. A depth of `32` requests exclusive
fullscreen; other nonzero depths are rejected. `GraphicsModes()` exposes the
selected display's RGBA8 modes through the familiar `TGraphicsMode` fields
(primary when selection is `-1`).
Refresh rates are rounded to integer Hz for this API; native mode selection keeps
the actual rational refresh rate. Hertz `0` selects the highest enumerated refresh
rate for the requested dimensions. Unsupported dimensions/rates fail explicitly.

`D3D11Displays()` returns a fresh snapshot of attached DXGI outputs with the primary
first. Each `TD3D11Display` contains `name`, desktop `x/y/width/height`, and `modes`.
Set `D3D11GraphicsDriver().display` before creating graphics: `0` selects the primary,
positive indices select another snapshot entry, and the default `-1` selects the
window's initial monitor. Device creation uses that output's adapter. Explicit
window coordinates are desktop coordinates; omitted coordinates centre on the
selected display (primary for the default selection).

The standard BRL `GraphicsModes()` list is cached. Set display selection before
first querying it; use the fresh `D3D11Displays()[index].modes` snapshot when
changing displays or responding to display-topology changes. Display indices are
snapshot positions, not stable identities. Refresh the snapshot after hotplug.

`SetFullscreen(enabled,width=0,height=0,hertz=0)` switches the current Max2D
window without replacing its images or device. Zero width/height use its current
client dimensions. Select the window with `SetRenderImage(Null)` first. Returning
to windowed mode restores its saved client area and position. With automatic
display selection, entry chooses the swap chain's containing output; explicit
selection stays on the chosen output. Moving across adapters does not migrate an
existing device: recreate graphics on the desired display if DXGI cannot enter
fullscreen there.

`SetBorderlessFullscreen(True)` fills the selected monitor without changing the desktop
resolution or refresh rate. `SetBorderlessFullscreen(False)` returns from borderless to
the saved window; it is a no-op in exclusive or ordinary windowed mode.
`SetFullscreen(False)` returns either fullscreen style to the saved window.
You can switch directly between borderless and exclusive: the original window
rectangle survives both transitions. Images and the device remain intact.
Borderless reports depth/hertz `0`, uses the original windowed drawing DPI, and
scales the backbuffer to fill the monitor. Use a virtual resolution for a fixed
application coordinate system. Resizing or positioning while borderless is rejected;
leave borderless first. Device recovery restores borderless mode as well.

Fullscreen resize chooses another supported display mode. Positioning an exclusive
fullscreen window is rejected. Alt+Enter is disabled; the application controls
switching explicitly. Minimized windows skip presentation. If DXGI drops exclusive
state, the driver attempts to reacquire it when the window regains foreground
focus. Temporary unavailability skips presentation rather than forcing focus.
Closing leaves exclusive mode before releasing the swap chain, restoring the
desktop. Device recovery restores the requested fullscreen mode as well.

The driver resizes flip-model buffers after transitions, including when dimensions
have not changed, following [Microsoft's flip-model requirements](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model).
Fullscreen can be unavailable in some remote sessions or while another application
owns the output; entry reports an error rather than silently choosing windowed mode.

`examples/d3d11_fullscreen.bmx` uses F10 for borderless, F11 for exclusive, and Escape to exit. It keeps a
fixed virtual resolution and displays virtual mouse coordinates for alignment
checks. `tests/d3d11_display.bmx` covers enumeration, repeated transitions,
geometry restoration, unchanged desktop mode in borderless, texture retention,
invalid modes and conventional fullscreen
creation. Building it with `-ud d3d11_recovery_test` additionally exercises device
replacement in both fullscreen styles. A test-only native helper activates the test window
for automated transitions, including an Alt activation gesture when the VM console
retains the foreground lock. Run this test interactively; production entry never
forcibly acquires focus.

### DPI scaling across fullscreen transitions

DXGI can promote an implicitly DPI-unaware Windows process on its first exclusive
fullscreen entry. The same client-size numbers can then represent fewer physical
pixels. The driver saves the window rectangle in physical screen coordinates and
uses a stable 96-DPI logical windowed drawing size. Initial window sizing also
accounts for a process that was already DPI-aware before graphics creation. Returning to windowed mode restores
both the physical footprint and the original backbuffer resolution; presentation
scales that backbuffer to the restored client area as needed. Fullscreen modes
continue to use their requested pixel dimensions.

Mouse-coordinate extents are queried separately from the drawable size, so
`WindowToVirtual`, `VirtualMouseX/Y` and virtual mouse warping stay aligned after
this change. Raw Windows mouse coordinates may reflect the new DPI awareness.
This preserves the initial drawing scale; it does not introduce a higher-resolution
windowed backbuffer or complete per-monitor DPI support.

The display regression test checks physical size, drawable resolution and input
mapping across repeated transitions at 200% Windows scaling. Passing `aware` to
the test also checks a process explicitly made DPI-aware before window creation. The DPI APIs are
resolved dynamically; this path is validated on Windows 11, not older Windows.

## Mipmaps

`MIPMAPPEDIMAGE` creates a full chain down to 1×1, including non-power-of-two
sizes. Combine it with `FILTEREDIMAGE` for trilinear minification; on its own it
uses nearest sampling and the nearest mip level. Query
`Max2DSupportsImageFlags(MIPMAPPEDIMAGE)` before relying on it: support is checked
against the device's RGBA8 texture, sampling, render-target and autogeneration
capabilities.

CPU uploads, render-image clears and drawing mark the chain dirty. Native
`GenerateMips` runs on the next sampled draw, after pending writes; unchanged
draws reuse it. `Max2DStats().mipmapGenerations` counts these generations.
Mipmapped CPU images are uploaded as premultiplied RGBA, including partial edits,
while their original CPU pixels remain straight-alpha. Render images already
use premultiplied storage. Sampling and readback keep the existing blend and
straight-alpha readback semantics.

The shared [mipmap limitations](mipmaps.md) apply: packed atlases are rejected,
animation cells get independent chains, manually created subviews share their
parent's chain, and alpha coverage is not preserved for MASKBLEND. There is no
new anisotropic or linear-light filtering. Hidden RGB at zero alpha is lost in
the GPU mipmapped copy.

`tests/d3d11_mipmaps.bmx` checks filter state, minification, lazy reuse, complete
and partial edits, transparent-colour fringes, target clears/draws, odd sizes,
animation isolation and atlas rejection. `examples/d3d11_mipmaps.bmx` compares
filtered drawing with and without mipmaps.

## Device recovery

The Max2D context checks device status before resource access and handles removal
reported during drawing, clearing, readback, resizing or presentation. It releases
its textures and pipeline before replacing the hardware device and swap chain on
the existing window. Normal window events and input continue using the same HWND.

Ordinary images retain an additional CPU copy of their uploaded base level.
Partial edits update that copy. Their GPU textures are recreated lazily, and
mipmaps regenerate when next sampled. Logical image/frame identity is preserved.
This adds approximately width × height × 4 bytes per uploaded ordinary image in
this context, in addition to existing core pixmaps and GPU storage.

Render images restart transparent after device replacement. Their viewport and
virtual-resolution settings survive, but applications must redraw their contents.
The interrupted frame is not replayed in full. Redraw the window each frame too.
`TD3D11Graphics.generation` increments after replacement, allowing advanced callers
to detect it; borrowed device/context/backbuffer interfaces become invalid.

If a device disappears during readback, the read fails explicitly after recovery;
redraw and retry rather than using incomplete pixels. If hardware-device or
pipeline creation fails, the error is surfaced without a busy retry loop. A later
rendering operation can retry, and `EndGraphics` remains safe while unavailable.
Resource-creation failures that occur during replacement are likewise explicit.
No WARP fallback or preservation of render-image contents is provided.

`tests/d3d11_recovery.bmx`, built with `-ud d3d11_recovery_test`, injects removal
status, presentation loss and a replacement failure. Successful recovery still
releases and recreates real hardware devices, swap chains, shaders and textures.
Run it separately from the normal tests:

```
bin\bmk.exe makeapp -r -ud d3d11_recovery_test mod\max2d.mod\tests\d3d11_recovery.bmx
```

This checks recovery mechanics; it does not simulate every driver failure or
establish real GPU-reset reliability on physical Windows hardware. Test injection
is absent from normal builds.

## Current limits

- One window; no widget attachment.
- Multi-monitor/multi-adapter, mixed-DPI and physical display hotplug validation
  remain outstanding; the development VM exposes one output.
- Windows x64 has been tested on the Windows 11 ARM64 Parallels VM through
  x64 emulation. Other Windows versions, native x64 hardware and 32-bit builds
  have not yet been validated.

From the SDK root:

```
bin\bmk.exe makeapp -r mod\pub.mod\direct3d11.mod\tests\layouts.bmx
bin\bmk.exe makeapp -r mod\pub.mod\direct3d11.mod\tests\device.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\d3d11_render.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\d3d11_window.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\d3d11_targets.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\d3d11_mipmaps.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\smoke.bmx
bin\bmk.exe makeapp -r -ud max2d_d3d11 mod\max2d.mod\tests\viewport.bmx
bin\bmk.exe makeapp -r -t gui -ud max2d_d3d11 mod\max2d.mod\examples\d3d11_hello.bmx
```

Run the resulting executables. Binding tests check 131 SDK structure sizes and
offsets, device creation and staging-texture mapping. Renderer tests cover all
blend modes, the MASK 127/128 boundary, drawing alpha, image edits, presentation
and reopening. The shared viewport test checks all pixels in 24 cases. Window
tests cover resize, letterbox edges, minimize/restore and edits while minimized.
The hello example provides virtual drawing and a native-resolution text overlay
for interactive inspection.

`examples/d3d11_render_images.bmx` demonstrates two rendering passes, translucent
shapes and text, tinting and enlarged filtered output. Target tests check alpha
conversion, target switching, readback, clipped clears, feedback rejection and
retention across window resizing.
